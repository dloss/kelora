# Timestamp fast-path pre-filter — results (2026-07-08)

Measures the `--since`/`--until` timestamp fast-path pre-filter (`extract_ts_only`)
that drops out-of-range lines before the full parse. See the spec and
`bench/README.md` for the harness.

## Setup

- Corpora: 1,000,000-line matched logfmt/JSON, timestamps spread uniformly at
  random across a 24h window and written **unsorted** (so a `--until`
  early-exit cannot help — the effect measured is the pre-filter's alone).
  Generated by `bench/gen_ts_corpus.py` (seeded, reproducible).
- `--since 2026-01-01T21:36:00Z` = the 90% mark (≈10% of events kept, ≈90%
  dropped). `--since 2026-01-01T00:00:00Z` = the 0% mark (all kept).
- Baseline = pre-change `main` (`702ded5`); candidate = this branch. Both
  release builds, run back-to-back per scenario. `bench_ts.py`, 9 runs + 2
  warmups, medians reported.
- **Host: shared, CPU-throttled cloud container.** Throughput was ~250k
  lines/s — roughly an order of magnitude below the same binaries on dedicated
  hardware. This matters for the conclusion (below).

## Numbers (median of 9, this host)

| ID | Scenario | logfmt | json |
|----|----------|--------|------|
| A | `--since 90%` (≈90% dropped), sequential | +3.5% | +5.3% |
| A | `--since 90%`, `--parallel`               | +2.6% | −4.7% |
| B | (json is the A/B pair above)              |   —    |   —  |
| C | `--since 0%` (all match), sequential      | −3.9% | **+7.8%** |
| D | no time filter (gate off)                 | −1.8% | +2.2% |
| E | `--levels error --since 90%`              | +19.1% | +9.1% |

(Positive = candidate faster. Earlier full-suite runs saw json scenario A/B
between +2% and +13% and logfmt between −14% and +3.5% — i.e. no stable signal.)

## Interpretation — the measurement is noise-bound on this host

Two cells prove the noise floor is roughly **±8%** here, so every single-digit
result above is indistinguishable from zero:

- **Scenario C-json = +7.8%** is *impossible* as a real gain. When every line
  matches (`--since 0%`), the candidate does `extract_ts_only` **plus** the full
  parse for every line — strictly *more* work than the baseline. It cannot be
  8% faster; that number is pure run-to-run variance.
- **Scenario D = ±2%** is the gate-off path (the pre-filter is inert — one
  branch per line). It must be 0%; the ±2% is variance.

So the honest reading is: on this throttled, shared container the effect of the
pre-filter is **within noise** for both formats, and the spec's ≥20% target for
scenario A (its kill criterion, §2.3/§7.2) **could not be demonstrated** — in
either direction. Scenario E's +19% is likewise unreliable given the ±8% floor.

### Why the win is masked here (and a note on logfmt)

The pre-filter's saving per dropped line is "don't build the `Event`/`FieldMap`."
Everything else the dropped line pays — reading it, walking its bytes to locate
the timestamp, and **parsing that timestamp** (the adaptive chrono parser, which
both paths must run to compare against the range) — is unchanged. When the host
is throttled so that I/O and scheduling dominate, the saved allocation is a small
slice of per-line cost and disappears into the noise.

For **logfmt** specifically, the effect ceiling is inherently lower than for
JSON: logfmt's full tokenizer (`parse_logfmt_pairs`) already walks every byte,
and the fast-path scan must walk them too, so only the field-map construction is
saved. JSON's full path deserializes into a `FieldMap` of `Dynamic`s, which is
heavier than the no-alloc scan — hence JSON is where a real win is most likely on
unthrottled hardware.

## Recommendation

Re-run `bench/bench_ts.py` on a dedicated, unthrottled machine before drawing a
merge conclusion. The implementation is correct and safe regardless of the perf
outcome:

- Invariant property test (`tests/ts_prefilter_invariant.rs`, 4000 random
  cases/parser + adversarial cases): `extract_ts_only` is always `None` or
  exactly the full parse's `parsed_ts`. Green.
- `bench/diff_ts_check.sh` (27 cases): byte-identical stdout/stderr/exit vs the
  baseline across the full flag matrix (strict, `--ts-field`, cascades,
  nested/numeric/dup-ts, no-ts, malformed, tz-bearing/naive, `--parallel`,
  `--stats`). Green.
- The safety gate keeps the pre-filter inert (one branch per line) whenever it
  is not provably safe, so runs without `--since`/`--until` are unaffected.
