    Privacy and Sanitization¶

    Strip personal data and secrets from a log before you share it, while keeping it useful. The recipes go from blunt to fine: drop fields, cut values down, replace patterns with placeholders, swap identifiers for stable pseudonyms, then check what's left. Most use checkout_pii.jsonl, a shop log with emails, IPs, card and phone numbers, and tokens in URLs and headers.

    Find what needs hiding¶

    --discover lists every field, nested ones included, with examples:

    kelora examples/checkout_pii.jsonl --discover

client_ip                      string        8    0%     5  "203.0.113.7", "198…
msg                            string        8    0%     8  "login ok", "paymen…

request.headers                map(1..2)     8    0%     —  
request.headers.user-agent     string        8    0%     3  "Mozilla/5.0", "cur…
request.path                   string        8    0%     7  "/login", "/api/ord…
user                           string        7   12%     3  "alice@example.com"…
session                        string        7   12%     3  "6f1c2a9e-4b7d-4e2a…
request.headers.authorization  string        4   50%     3  "Basic YWxpY2U6czNj…

    Free text (msg here) needs a look of its own: personal data hides in messages, URLs and headers as often as in named fields.

    Keep only the fields you need¶

    List the fields to keep, not the ones to drop. A field added to the log next month then stays out until you add it:

    kelora examples/checkout_pii.jsonl -k timestamp,level,service,msg -n 3

    timestamp='2026-10-06T09:14:02Z' level='INFO' service='auth' msg='login ok'
timestamp='2026-10-06T09:14:31Z' level='INFO' service='checkout'
  msg='payment authorized card=4111 1111 1111 1111 amount=42.00'
timestamp='2026-10-06T09:15:10Z' level='ERROR' service='checkout'
  msg='card 5555555555554444 declined for bob@example.org, retry from 198.51.100.23'

    -K session,user does the opposite. Both only shape the output: filters, --freq and metrics still see every field. To remove a field before they run, do it in a script: e = e.keep(["timestamp", "level", "service", "msg"]), e = e.drop(["session"]) or e.session = ().

    Remove a nested field¶

    -k and -K act on top-level fields only. Remove a nested key with remove_path(); events without it are left alone:

    kelora examples/checkout_pii.jsonl -e 'e.remove_path("request.headers.authorization")' -k request -n 2

    request={"headers":{"user-agent":"Mozilla/5.0"},"path":"/login"}
request={"headers":{"user-agent":"Mozilla/5.0"},"path":"/api/orders?token=f9a8c7e6d5&page=2"}

    e.request.headers.authorization = () would leave "authorization": null.

    Cut values down¶

    Keep the part you need: the network instead of the address, the email domain instead of the person, the path without its query string (which often carries tokens):

    kelora examples/checkout_pii.jsonl \
  -e 'e.client_ip = e.client_ip.mask_ip(2);
      if e.has("user") { e.user = e.user.parse_email().domain }
      e.path = e.request.path.split("?")[0];' \
  -k client_ip,user,path

    client_ip='203.0.0.0' user='example.com' path='/login'
client_ip='203.0.0.0' user='example.com' path='/api/orders'
client_ip='198.51.0.0' user='example.org' path='/api/orders'
client_ip='198.51.0.0' user='example.org' path='/login'
client_ip='192.0.0.0' user='example.net' path='/support/callback'
client_ip='192.0.0.0' user='example.net' path='/api/kyc'
client_ip='10.0.0.0' path='/internal/webhooks'
client_ip='203.0.0.0' user='example.com' path='/api/orders/1042'

    mask_ip(n) zeroes the last n octets (IPv6: groups). shorten(8, "") keeps the first 8 characters of a value.

    Fail closed¶

    If a script fails on an event, kelora outputs the event as it was before the script ran, with the data you meant to hide, and warns on stderr. Here the webhook event has no user:

    kelora examples/checkout_pii.jsonl \
  -e 'e.client_ip = e.client_ip.mask_ip(2); e.user = e.user.parse_email().domain' \
  -k client_ip -n 7

    client_ip='203.0.0.0'
client_ip='203.0.0.0'
client_ip='198.51.0.0'
client_ip='198.51.0.0'
client_ip='192.0.0.0'
client_ip='192.0.0.0'
client_ip='10.0.4.12'
🔸 Exec errors: 1 total
  examples/checkout_pii.jsonl:7: Missing field during expression evaluation. Check field names, or use e.has(...) / e.get_path(...) when the field is optional.
  🔸 1 event was output without the changes of the --exec stage that failed on it. A stage calls mask_ip(), so it may still hold data it was meant to hide. Add --strict to stop at the first error instead, and guard optional fields with e.has(...).

    10.0.4.12 slipped through. When sanitizing, add --strict: the first error stops the run with exit code 1, before the event is written:

    kelora examples/checkout_pii.jsonl --strict \
  -e 'e.client_ip = e.client_ip.mask_ip(2); e.user = e.user.parse_email().domain' \
  -k client_ip -n 7

    client_ip='203.0.0.0'
client_ip='203.0.0.0'

    Then guard optional fields with e.has(...), as in the recipe above.

    Replace personal data in free text¶

    normalized() replaces addresses, IDs and the like inside text with placeholders. Card, phone and US social security numbers are off by default; name them:

    kelora examples/checkout_pii.jsonl \
  -e 'e.msg = e.msg.normalized(["email", "ipv4", "ipv6", "credit_card", "phone", "ssn"])' \
  -k service,msg

    service='auth' msg='login ok'
service='checkout' msg='payment authorized card=<credit_card> amount=42.00'
service='checkout'
  msg='card <credit_card> declined for <email>, retry from <ipv4>'
service='auth' msg='login failed for <email>: password=hunter2 rejected'
service='support' msg='callback requested at <phone> by <email>'
service='kyc' msg='identity check passed ssn=<ssn>'
service='webhooks'
  msg='retrying delivery to https://hooks.example.com/orders?api_key=sk_live_8f3K2mQ9xLp4 after timeout'
service='checkout' msg='order 1042 shipped to <email>'

    Card numbers must pass the Luhn check, so other long numbers stay. Called on the event, e = e.normalized([...]) rewrites every string field, nested ones included. The full pattern list also has uuid, url, mac, path and hashes.

    Redact secrets with a regex¶

    Passwords and API keys have no fixed shape, but they usually follow a known name:

    kelora examples/checkout_pii.jsonl \
  -e 'e.msg = e.msg.replace_regex("(password|api_key|token)=[^&\\s]+", "${1}=***")' \
  -k msg --filter 'e.msg.contains("***")'

    msg='login failed for bob@example.org: password=*** rejected'
msg='retrying delivery to https://hooks.example.com/orders?api_key=*** after timeout'

    Consistent pseudonyms¶

    pseudonym() replaces a value with a keyed alias. The same input gives the same alias as long as KELORA_SECRET stays the same, so you can still count, join, and follow a user across files:

    KELORA_SECRET=change-me kelora examples/user-data.jsonl \
  -e 'e.user = pseudonym(e.email, "user"); e.email = (); e.ip = e.ip.mask_ip(1)' -k user,action,ip

    user='g8tM8VSw0JPXBMVPhDpsj0Zf' action='login' ip='192.168.1.0'
user='VBFT1D7bynhXWHogMn2-JsRh' action='purchase' ip='10.0.5.0'
user='MaUceTZy9kaE5V2HOavznCDY' action='view' ip='172.16.88.0'
user='Tq9oFjjc-1WvdC9mCHqAC5YQ' action='logout' ip='192.168.1.0'
user='4q0StVl3bHi6gqkOSXZzOA8f' action='login' ip='10.0.5.0'

    The second argument is a domain: the same value in two domains gets unrelated aliases. Don't use hash() for this: it's unkeyed, so anyone can hash a list of candidate emails and match them.

    Pseudonymize every IP and email address¶

    --pseudonymize ip,email replaces every address in every field, nested values and messages included, with a keyed token. Card numbers are untouched:

    KELORA_SECRET=change-me kelora examples/checkout_pii.jsonl \
  --pseudonymize ip,email -k user,client_ip,msg -n 3

    user='<email:RIf3Lw9s5T04dtVK1ZehhKBA>'
  client_ip='<ip:K12uPb8OQcdvdsigV03GIDbf>' msg='login ok'
user='<email:RIf3Lw9s5T04dtVK1ZehhKBA>'
  client_ip='<ip:K12uPb8OQcdvdsigV03GIDbf>'
  msg='payment authorized card=4111 1111 1111 1111 amount=42.00'
user='<email:yQV5MLU96Qw3tOs6V3mLXqkO>'
  client_ip='<ip:75CgnUwejaQQUW_irMcQGSxb>'
  msg='card 5555555555554444 declined for <email:yQV5MLU96Qw3tOs6V3mLXqkO>, retry from <ip:75CgnUwejaQQUW_irMcQGSxb>'

    It runs right after parsing, so filters, --freq and --discover see only tokens. --stats counts the replacements (Addresses pseudonymized: 9 IP, 11 email). extract_ip() returns the tokens, so you can still count failed logins per source address without seeing one:

    KELORA_SECRET=change-me kelora examples/sshd_auth.log --input-year 2024 \
  --pseudonymize ip --filter 'e.msg.starts_with("Failed password")' \
  -e 'e.src = e.msg.extract_ip()' --freq src

    src          (3 values):
  value                          count
  <ip:wuukJmb_X0e9Dmt1FaY0h3SU>      4
  <ip:75CgnUwejaQQUW_irMcQGSxb>      2
  <ip:BqgbtaN-gmRl5rBJAHQokX0m>      1

    A filter never sees a real address either. To look for a known one, pseudonymize the literal the same way:

    KELORA_SECRET=change-me kelora examples/sshd_auth.log --input-year 2024 \
  --pseudonymize ip --filter 'e.msg.contains("198.51.100.23".pseudonymize_ips())' -k msg

    msg='Failed password for invalid user oracle from <ip:75CgnUwejaQQUW_irMcQGSxb> port 51002 ssh2'
msg='Failed password for invalid user test from <ip:75CgnUwejaQQUW_irMcQGSxb> port 51188 ssh2'

    For one field only, use pseudonymize_ips() or pseudonymize_emails() in --exec.

    Find the address behind a token¶

    Tokens can't be reversed, but whoever holds the secret and the original log can look one up, say after a recipient reports <ip:wuukJmb_X0e9Dmt1FaY0h3SU>:

    KELORA_SECRET=change-me kelora examples/sshd_auth.log --input-year 2024 \
  --filter 'e.msg.pseudonymize_ips().contains("<ip:wuukJmb_X0e9Dmt1FaY0h3SU>")' -k msg -n 1

    msg='Failed password for invalid user admin from 203.0.113.77 port 40122 ssh2'

    Pseudonymize IPs but keep subnets¶

    --pseudonymize ip-prefix replaces each address with another of the same family; addresses that share a prefix still share one afterwards (10.0.5.23 and 10.0.5.24 stay in one /24):

    KELORA_SECRET=change-me kelora examples/user-data.jsonl \
  --pseudonymize ip-prefix -k user_id,ip

    user_id='user001' ip='64.168.98.21'
user_id='user002' ip='245.126.84.248'
user_id='user003' ip='50.206.38.29'
user_id='user004' ip='64.168.98.20'
user_id='user005' ip='245.126.84.246'

    Pseudonymize a network the same way to filter by it:

    KELORA_SECRET=change-me kelora examples/user-data.jsonl --pseudonymize ip-prefix \
  --filter 'e.ip.is_in_cidr("10.0.0.0/8".pseudonymize_ips("prefix"))' -k user_id,ip

    user_id='user002' ip='245.126.84.248'
user_id='user005' ip='245.126.84.246'

    Prefixes are exactly what an attacker can use against it; for data that leaves your control, prefer --pseudonymize ip (trade-offs).

    Keep the secret out of shell history¶

    Use one long random secret per recipient, so two recipients can't link their copies, and pass it as a file:

    openssl rand -base64 24 > vendor-a.key
KELORA_SECRET_FILE=vendor-a.key kelora app.jsonl --pseudonymize ip,email -F json -o for-vendor-a.jsonl

    Without a secret, kelora uses a random one and the pseudonyms change on every run.

    Sanitize a text log and keep its format¶

    Read the file as plain lines and print them back unchanged, apart from the replacements:

    KELORA_SECRET=change-me kelora examples/sshd_auth.log -f line --pseudonymize ip -k line -b -n 3

    Mar  3 06:12:01 bastion sshd[4121]: Accepted publickey for deploy from <ip:j7lEFbSZvlI4erFlvAwUxbzf> port 52114 ssh2: ED25519 SHA256:q2Xw
Mar  3 06:14:22 bastion sshd[4188]: Failed password for invalid user admin from <ip:wuukJmb_X0e9Dmt1FaY0h3SU> port 40122 ssh2
Mar  3 06:14:25 bastion sshd[4188]: Failed password for invalid user admin from <ip:wuukJmb_X0e9Dmt1FaY0h3SU> port 40122 ssh2

    Add -e 'e.line = e.line.normalized([...])' or replace_regex() for other data.

    Check what's left¶

    Run the sanitized output through kelora again and count which kinds of personal data remain:

    KELORA_SECRET=change-me kelora examples/checkout_pii.jsonl --pseudonymize ip,email -F json \
  | kelora -j -m -e 'let t = e.to_json();
      for p in ["email", "ipv4", "ipv6", "credit_card", "phone", "ssn"] {
        if t.normalized(p) != t { track_freq("left", p) }
      }'

    left         (3 values):
  value        count
  credit_card      2
  phone            1
  ssn              1

    The pseudonymized addresses are gone; card, phone and SSN numbers are not. Patterns find what has a shape. Names, street addresses and free-form secrets don't, so read a sample as well.

    All together¶

    Fields chosen, secrets and numbers redacted, addresses pseudonymized, query strings cut, stopping on any error. Add -o shared.jsonl to write a file:

    KELORA_SECRET=change-me kelora examples/checkout_pii.jsonl --strict \
  --pseudonymize ip,email \
  -e 'e.path = e.request.path.split("?")[0];
      e.msg = e.msg
        .replace_regex("(password|api_key|token)=[^&\\s]+", "${1}=***")
        .normalized(["credit_card", "phone", "ssn"]);' \
  -k timestamp,level,service,user,client_ip,path,msg -F json -n 4
