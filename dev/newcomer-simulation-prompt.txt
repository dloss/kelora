Simulate a new user trying Kelora for the first time. Think out loud as
that user: first impressions, what you expected, where you hesitate, what
makes you want to keep going or give up. Be realistic, not polite.

Vary the run. Earlier runs covered certain ground, so don't repeat it:
- Skim CHANGELOG.md [Unreleased] and `git log --oneline -40` to see what
  recent sessions found and fixed; steer away from those areas.
- Choose a combination of the options below that recent runs haven't
  covered, and state it in one line at the top of your report. Don't use the
  examples in brackets as a checklist; they only show the range.
  - Who: background, role and what brought them here [sysadmin on call,
    developer debugging their own service, security analyst, data person,
    someone moving off another tool].
  - Entry point: where they first meet kelora [README, kelora.dev page,
    a cookbook recipe, `-h`, a colleague's one-liner].
  - Logs: a kind of log you haven't tried before. Real files on this machine
    count, and so do realistic made-up samples of what that person has.
    Put scratch files in the scratchpad, never in the repo.
  - Task: one concrete goal that person would have, worked through to an
    answer, not a tour of features.
  - Surface: one or two less-travelled parts of the CLI or the Rhai/function
    library that come up on the way to that goal.
- Use the dev build (`cargo build`, ./target/debug/kelora) as "installed"
  kelora. Use the release binary only if you check performance, and note how
  old it is.

How to play the user:
- Guess the syntax first, the way that person would (from the tools they
  already know); only then read -h / --help-* / the docs.
- Make the mistakes that person would plausibly make, not a fixed list.
- When the obvious route fails, try what a real user tries next (another
  flag, a docs search, giving up and piping to another tool) and note which
  of these kelora made easy.

When something goes wrong, step out of the role and find the cause:
- Reproduce it minimally and vary inputs until you know the exact trigger.
- Read the relevant source and point to file:line. Tell "wrong data shown
  with exit 0" (worst) apart from "noisy" or "confusing wording".
- Check whether the docs/help teach the wrong thing (examples that are
  actually buggy count double).

Report:
1. A short narrative of how it felt: what sells it, and where I stumbled,
   in order.
2. A table of fixes ranked smallest/safest first: problem → where (file:line)
   → size (trivial/small/medium/needs decision) → kind (additive / bug fix /
   behaviour change). Prefer fixes that don't add much complexity.
3. Smaller notes (fixtures, stale docs, wording).

Don't break existing behaviour. Users have scripts, configs and habits
built on current output, flags and exit codes. Prefer additive fixes: a hint,
a clearer error, a doc fix, a new option.
- A bug fix may change behaviour, but only where the current behaviour
  contradicts the docs/help or is obviously not what was meant (wrong data,
  silently dropped events, a crash). Cite the doc line or explain why it's
  obviously unintended.
- If the behaviour is merely surprising, undocumented, or arguable, it isn't
  a bug: propose it as "needs decision", don't fix it.
- When unsure, treat it as a behaviour change and ask.
- For every behaviour-changing fix, say who could notice (output format,
  exit codes, which events match) and add a CHANGELOG entry that says so.

Don't change code during the simulation. After I pick items:
- Implement each with a test, following CLAUDE.md conventions (rule of
  silence: hints vs warnings vs errors; data-only modes hide hints).
- For changes to auto-detection or format regexes, run the base-vs-head
  regression check over the local real-log corpus before committing.
- Run just fmt, just lint, just test, just docs-check; add CHANGELOG
  entries (symptom → fix → action); commit in reviewable pieces.
